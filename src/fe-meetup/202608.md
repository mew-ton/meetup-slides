## Oxlint

2026/07/22

---

## "Oxlint" とは

- Rust 製の JavaScript / TypeScript 向け Linter (コードの書き方を検査するツール)
- 定番の ESLint と同じ役割を, 桁違いの速さで実行することを目指している
- Vite を開発する VoidZero (2026 年 6 月に Cloudflare が買収) が開発している

---

## Oxlint のニュース

**型情報を使った Lint が正式版に — ESLint 比で最大 18 倍**

- 7/22, 型を見る Lint (type-aware) が実験版から **安定版** へ
- typescript-eslint が持つ型ありルール **61 個のうち 59 個** をカバー
- VS Code 規模のコードベースで **ESLint + typescript-eslint の最大 18 倍** 速い
- 設定は `typeAware: true` の 1 行

<!-- _footer: "出典: [Type-Aware Linting Stable (Oxc)](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)" -->

---

## なぜこれが大きいのか

- Lint には **書き方だけ見るもの** と **型情報まで見るもの** の 2 種類がある
  - 「Promise の `await` 忘れ」のようなバグは, 後者でないと見つけられない
- 型ありルールは重く, ESLint では CI で数分かかることも珍しくなかった
- Oxlint は速さが売りだったが, **型ありルールが無い** ことが最大の弱点だった
  → 「速いが物足りない」から「置き換え候補」へ

---

## TypeScript 7 との関係

- 型を見る部分は **tsgolint** という別エンジンが担当している
- tsgolint は 7/8 に正式リリースされた **Go 製の TypeScript 7 コンパイラの上に直接構築**
  (TypeScript 7.0 = コンパイラを Go へ書き直し, 型チェックを約 10 倍高速化した版)
- Lint と型チェックが **同じ型情報を共有** するため, 二重に解析しなくて済む
- 一方 ESLint 側は, 型情報を取り出すための API が TypeScript 7 でまだ未提供
  → **型ありルールは TypeScript 6 系で動かす** 必要がある状態が続いている

## Google Chrome

2026/07/28

![bg 15%](./_assets/logos/googlechrome.png)

---

## "Google Chrome" とは

- Google が開発する, デスクトップで圧倒的シェアを持つ Web ブラウザ
- レンダリングエンジンは Blink, 新しい CSS / Web API の実装を積極的に主導
- Edge など他の Chromium 系ブラウザの基盤にもなっている

---

## Google Chrome のニュース

**Chrome 151 — SPA の "画面遷移" がようやく計測できるようになった**

- `soft-navigation` : JavaScript による **画面内の遷移** を 1 回の遷移として記録
- `interaction-contentful-paint` : 操作後に **新しい内容が描画されるまで** を計測
- `<usermedia>` : カメラ / マイクの利用許可を **HTML の要素として** 置ける新タグ
- Web Crypto に **耐量子計算機暗号** (ML-KEM / ML-DSA) が試験的に追加

<!-- _footer: "出典: [New in Chrome 151 (Chrome for Developers)](https://developer.chrome.com/blog/new-in-chrome-151)" -->

---

## 何が嬉しいのか

- 従来の計測 API は **ページを読み込み直す遷移** しか見えていなかった
- React / Next.js のような SPA (画面をページ再読み込みなしで切り替える作り) では,
  1 セッションで 5 回画面を移動しても **計測されるのは最初の 1 回だけ**
  → 残り 4 回は "存在しない遷移" として扱われていた
- Core Web Vitals (Google が定める体感速度の指標) を **画面ごとに** 出せるようになる
  → 「どの画面が遅いのか」が, ようやく数字で分かる

---

## 他ブラウザとの互換性

| 機能                       | Chrome / Edge | Safari    | Firefox |
| -------------------------- | ------------- | --------- | ------- |
| `soft-navigation` 等の計測 | 151〜         | —         | —       |
| `<usermedia>`              | 151〜         | —         | —       |
| `shadowrootslotassignment` | 151〜         | 27 (先行) | 151〜   |

- 計測系は **非対応でも表示は変わらない** → 段階的強化で使える
- `<usermedia>` は許可 UI そのもの → 非対応ブラウザには **JS API の併用が必須**

---

## 来月から Chrome は 2 週間ごとになる

- 9/8 の **Chrome 153** から, 安定版のリリース間隔が **4 週間 → 2 週間** へ
- 対象はデスクトップ / Android / iOS のすべて. 年間 約 26 バージョンになる
- 1 回の変更量が減るため, 不具合の切り分けがしやすくなるとしている
- 企業向けの Extended Stable は 8 週間のまま

<!-- _footer: "出典: [Get features faster with Chrome's two-week release cycle (Chrome for Developers)](https://developer.chrome.com/blog/chrome-two-week-release)" -->

## Cloudflare

2026/08/06

---

## "Cloudflare" とは

- 世界中の Web サイトが利用する CDN (配信を高速化する仕組み) / セキュリティ事業者
- 利用者に近いサーバでコードを動かす実行基盤 **Workers** を提供している
- 2026 年 6 月に Vite の開発元 VoidZero を買収し, フロントエンド基盤側にも進出した

---

## Cloudflare のニュース

**"Kitesurf" — Chromium を使わずに作られたブラウザが登場**

- 8/6 公開. **Chromium を一切使わず**, Workers の V8 隔離環境だけで動くブラウザ
- HTML の処理には Rust 製の **Blitz**, CSS エンジンには Firefox の **Stylo** を採用
- **Chrome DevTools Protocol 互換** — Puppeteer / Playwright がそのまま繋がる
- スクリーンショット 1 枚あたり CPU **1,173ms → 380ms**, メモリ **271MiB → 58MiB**

<!-- _footer: "出典: [Introducing Kitesurf: The agent-first browser that runs in V8 isolates on Cloudflare Workers (Cloudflare Blog)](https://blog.cloudflare.com/kitesurf/)" -->

---

## なぜフロントエンドの話なのか

- 想定用途は **AI エージェント** だが, 中身は「画面を持たないブラウザ」
  → E2E テストや OGP 画像生成で使う **ヘッドレスブラウザの置き換え候補** になる
- この用途は実質 Chromium 一択で, 1 プロセスあたりの資源消費が重いのが定番の悩みだった
- ただし **実時間 (待ち時間) は Chromium の約 1.8 倍遅い** — 省資源とのトレードオフ
- ベータ期間は無料で試せる. 将来的な OSS 化も表明されている

---

## ブラウザエンジンを作り直す, という流れ

- ブラウザの中核 (エンジン) は Blink / WebKit / Gecko の 3 系統に集約されて久しい
- 一方で近年, **Rust で部品ごとに作り直す** 試みが実用水準に育ってきている
  - Blitz : レイアウトと描画を担う Rust 製エンジン
  - Stylo : Firefox が実際に使っている CSS エンジン. 単体で再利用できる
- Kitesurf は, その部品を組み合わせて **第 4 のエンジンを実際に商用投入した** 例

## JavaScript

2026/08/13

![bg 15%](./_assets/logos/javascript.png)

---

## "JavaScript" とは

- Web ブラウザ上で動作する, フロントエンド開発の中心となるプログラミング言語
- 言語仕様は ECMAScript として標準化され, 毎年 1 回改訂される
- 実装はブラウザごとに異なり, Chrome は V8, Firefox は SpiderMonkey,
  Safari は JavaScriptCore を使う

---

## JavaScript のニュース

**`using` 構文が, 3 大エンジンすべてで動くようになった**

- 8/13 公開の **Safari 先行版 (Safari Technology Preview 250)** が
  Explicit Resource Management (明示的なリソース管理) に対応
- `using` / `await using`, `Symbol.dispose`, `DisposableStack` を含む完全対応
- これで **V8 / SpiderMonkey / JavaScriptCore** の 3 エンジンが出揃った
- TypeScript で書いて変換していた構文が, **変換なしで動く** 段階に入る

<!-- _footer: "出典: [Release Notes for Safari Technology Preview 250 (WebKit)](https://webkit.org/blog/18191/release-notes-for-safari-technology-preview-250/)" -->

---

## "using" とは何か

- ブロックを抜けるときに **後片付けを自動で呼ぶ** 変数宣言
  - ファイル, DB 接続, ロックなど「開いたら必ず閉じる」対象が想定用途
- `try { ... } finally { close() }` の書き忘れを, 構文レベルで防げる
- 複数ある場合は **宣言と逆順** に片付けられる. 非同期版が `await using`
- Java の try-with-resources, C# の `using`, Python の `with` に相当する機能

---

## 使えるようになるのはいつか

- Safari は **先行版での対応** — 製品版 (通常の Safari) への搭載はこれから
- Chrome / Firefox は既に安定版で利用可能
- 当面は TypeScript による変換を併用するのが安全
  → 「変換なしで書ける」と言い切れるのは, Safari 製品版に載ってから

## keyv

2026/08/04

---

## "keyv" とは

- 保存先 (メモリ / Redis / ファイル) を問わず同じ書き方で使えるキャッシュ用ライブラリ
- 単体で使うより, **他のライブラリの依存として入ってくる** ことが圧倒的に多い
- 同じ作者の `flat-cache` / `file-entry-cache` と合わせ **週 1 億 DL 超** の規模

---

## 直前に, npm 側で起きていたこと

- 7/28, npm は **公開時のマルウェアスキャン** を導入
  - 公開されたパッケージは, 検査を通るまで install できない
    (公開完了まで 5〜15 分ほどの遅延が入る)
- 正規の用途で危険な処理を含むパッケージ向けに, `contentPolicy` 宣言の仕組みも追加
- 「レジストリ側で水際を止める」方向への, npm としては大きな一歩だった

<!-- _footer: "出典: [npm publish-time malware scanning and dual-use metadata (GitHub Changelog)](https://github.blog/changelog/2026-07-28-npm-publish-time-malware-scanning-and-dual-use-metadata/)" -->

---

## keyv のインシデント

**"ChainDrop" — 約 450 パッケージが 4 時間で汚染された自己増殖ワーム**

- 8/4 9 時 (UTC), keyv 作者の **GitHub アカウントが乗っ取られる**
- main ブランチへ直接 push され, **本人の GitHub Actions が発火**
  → 正規の署名付きで, 悪意あるバージョンが npm に公開された
- 汚染は **約 450 パッケージ / 2,200 バージョン以上**, 合計 月間 約 20 億 DL 規模
- 盗んだ資格情報で **他のパッケージにも自分を仕込む** ワーム型

<!-- _footer: "出典: [Shai-Hulud strikes again: CHAINDROP worm hits 400+ npm packages (Elastic Security Labs)](https://www.elastic.co/security-labs/shai-hulud-chaindrop-npm-supply-chain)" -->

---

## 何を盗み, どう増えたのか

- `preinstall` (インストール直前に走るスクリプト) で **Bun を勝手にダウンロード** し,
  728KB の難読化されたプログラムを実行
- 狙われたのは npm のトークン, GitHub / AWS の資格情報, Kubernetes 設定, 暗号資産の鍵
- 盗んだ公開権限で **他のパッケージの最新版を取得 → 自分を混ぜ → パッチ版として公開**
- これを自動で繰り返すことで, 無関係な作者のパッケージまで連鎖的に汚染された

<!-- _footer: "出典: [ChainDrop supply chain compromise (Microsoft Security Blog)](https://www.microsoft.com/en-us/security/blog/2026/08/04/chaindrop-supply-chain-compromise-anatomy-self-propagating-worm/)" -->

---

## "Shai-Hulud" の系譜

- 2025 年から続く, **npm を狙う一連のワーム型マルウェアの総称**
- 共通する特徴は「盗んだ資格情報で, 次のパッケージを汚染する」自己増殖の仕組み
- 2026 年 5 月には派生版 (Mini Shai-Hulud) が TanStack などを汚染した
- 今回の ChainDrop はその系譜の最新版 — 手口が洗練され, 規模が桁違いになった

---

## なぜ止められなかったのか

- 公開時スキャン導入の **わずか 7 日後** の事案
- 正規の CI から, 正規の署名付きで公開された
  → 「不正な公開」ではなく **正規の公開手順そのもの** が乗っ取られている
- npm v12 は install スクリプトを既定で止めるが, **v11 以前の環境は無防備**
- 悪意あるバージョンが最新版として残った時間は数時間 — その間の install が被害に

---

## 教訓

**新しいバージョンは, 数日寝かせてから入れる**
— 悪意あるバージョンの多くは, 数時間のうちに発見・削除される

- pnpm 11 は「公開から 1 日経っていない版は入れない」を **既定で有効化済み**
  (Yarn にも同等の設定がある)
- npm も `min-release-age` で同じことができる — ただし **既定は無効, 自分で書く**
- 併せて, npm CLI は **v12 以降** に上げておく
